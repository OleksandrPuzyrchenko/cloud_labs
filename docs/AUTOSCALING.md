# Автоматичне масштабування

Файл: `app/terraform/autoscaling.tf` (AWS Application Auto Scaling для ECS Fargate).

## Параметри

| Параметр | Значення | Пояснення |
|---|---|---|
| min_capacity | 1 | Мінімум для економії; сервіс завжди доступний |
| max_capacity | 4 | Обмеження лабораторної; захист бюджету |
| Тип політики | Target tracking | AWS сам розраховує кількість задач, щоб тримати метрику біля цілі |
| Метрика | `ECSServiceAverageCPUUtilization` | Середнє CPU по всіх задачах сервісу |
| target_value | 60% | Див. нижче |
| scale_out_cooldown | 60 с | Додавати екземпляри швидко |
| scale_in_cooldown | 300 с | Вилучати обережно |

### Чому 60%
Запас 40% дозволяє витримати стрибок трафіку під час запуску нового екземпляра (30–90 с: старт Fargate-задачі + health check ALB). Якщо ціль 90% — CPU досягне 100% раніше, ніж з'явиться допомога, і зросте латентність. Якщо 30% — платимо за майже порожні екземпляри.

## Період стабілізації (cooldown)
Cooldown — це мінімальний час після масштабування, протягом якого політика не виконує наступну дію того ж напряму. Нові екземпляри потребують часу, щоб прогрітися та вплинути на метрику; cooldown дає змогу побачити результат попередньої дії перед наступним рішенням.

Якщо встановити **0**: після кожної точки метрики політика може одразу додавати/вилучати задачі. Метрика ще не відображає ефект попереднього кроку (нова задача не прогріта), тому виникає надмірне масштабування вгору, а при спаді — різке вилучення і знову додавання, нестабільна латентність, зайві витрати та відмови під час старту/зупинки задач.

## Як перевірити
```bash
cd app/terraform
terraform apply
aws application-autoscaling describe-scalable-targets --service-namespace ecs
aws application-autoscaling describe-scaling-policies --service-namespace ecs
```


## Панель моніторингу

CloudWatch dashboard `cloud-lab-autoscaling` (`app/terraform/dashboard_scaling.tf`), 5 графіків:

| # | Графік | Метрика |
|---|---|---|
| 1 | Бажана і фактична кількість екземплярів | `ECS/ContainerInsights` `DesiredTaskCount`, `RunningTaskCount` (для цього в кластері ввімкнено Container Insights) |
| 2 | Завантаження CPU (з лінією цілі 60%) | `AWS/ECS` `CPUUtilization` |
| 3 | Запити за хвилину | `AWS/ApplicationELB` `RequestCount` (Sum, 60 с) |
| 4 | Латентність p95 | `AWS/ApplicationELB` `TargetResponseTime` (p95) |
| 5 | Відповіді 5xx | `AWS/ApplicationELB` `HTTPCode_Target_5XX_Count` |

### Чому між перетином порогу і появою екземпляра минає час
1. CloudWatch отримує метрику CPU з ECS із періодом 1 хв, тож дані запізнюються.
2. Target tracking створює alarm, який спрацьовує лише після кількох поспіль точок вище цілі (3 хвилини для scale-out).
3. Після рішення Fargate має завантажити образ, запустити контейнер, а ALB — пройти health check. Це ще 30–90 с.

### Чому вилучення значно пізніше за спад навантаження
Scale-in свідомо повільніший: alarm вимагає 15 хвилин (15 точок) метрики нижче цілі, плюс `scale_in_cooldown` = 300 с. Причина асиметрії: зайвий екземпляр коштує копійки, а нестача — це деградація сервісу; крім того, повільне вилучення запобігає флапінгу, коли короткий спад викликав би видалення задачі і одразу її повторне додавання.
