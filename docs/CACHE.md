# Кешування читання

## Реалізація
- `GET /api/notes` (найнавантаженіше читання: список росте з кожним записом) працює за схемою **cache-aside** (`app/index.js`):
  1. перевірка Redis (ключ `notes:list`); якщо є — повертається з `X-Cache: HIT`;
  2. інакше `SELECT` з PostgreSQL;
  3. результат зберігається в Redis з TTL **30 с** і повертається (`X-Cache: MISS`).
- Якщо Redis недоступний — сервіс читає з бази.
- Redis — AWS ElastiCache (`app/terraform/redis.tf`), доступний лише з security group ECS-задач.
- Перемикач: змінна Terraform `cache_enabled` -> змінна середовища `CACHE_ENABLED`.
- Кеш спільний для всіх екземплярів. Кеш у пам'яті процесу тут не підходить: кожен екземпляр мав би власну копію, тож клієнти, потрапляючи на різні екземпляри, бачили б різні дані, а після масштабування нові екземпляри починали б з порожнім кешем.

## Результати

Сценарій `loadtest/script.js`, N = 50, однакові умови.

| Показник | Без кешу | З кешем |
|---|---|---|
| Латентність p95 (k6, мс) | 9170ms | 589.81ms |
| Запитів за секунду (http_reqs/s) | 4486 (8.284649/s) | 88200 (163.311675/s) |
| CPU бази (RDS), середнє / максимум % | 5.7% / 7.58% | 5.5% / 6.95% |
| Підключень до бази (макс.) | 17 | 18 |
| Макс. кількість екземплярів | 4 | 4 |

Частка влучань у кеш (ElastiCache `CacheHits = 26347` / (`CacheHits = 26347` + `CacheMisses = 113`)): 
99.57 %

Кеш збільшив пропускну здатність у ~20 разів і зменшив p95 у ~15 разів

## Актуальність даних
Після запису (`POST`) закешований список не змінюється, поки не мине TTL, тож клієнт може бачити застарілі дані **до 30 секунд** (у гіршому випадку — запис зроблено одразу після заповнення кешу).


Як зменшити:
- зменшити TTL (ціною більшої кількості звернень до бази);
- оновлювати кеш при записі (write-through).
