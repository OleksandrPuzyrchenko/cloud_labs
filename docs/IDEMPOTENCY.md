# Ідемпотентність записів

## Яку проблему розв'язує
Клієнт надсилає `POST`, але через обрив зв'язку, таймаут або втрату відповіді не знає, чи запит виконано, і повторює його. Без захисту виходять **дублікати** (два однакові записи, два списання коштів тощо). Заголовок `Idempotency-Key` дозволяє безпечно повторювати запит: повторний запит із тим самим ключем не виконується вдруге, а повертає збережений результат першого.

## Реалізація
(`app/index.js`, middleware `idempotency` для `POST /api/notes`)
1. Клієнт передає унікальний ключ (наприклад, UUID) у заголовку `Idempotency-Key`. Без заголовка поведінка не змінюється.
2. Сервіс атомарно виконує `SET idem:<ключ> NX EX 86400` у Redis. Лише один із паралельних запитів отримує право виконати операцію.
3. Перший запит виконується, його статус і тіло зберігаються в Redis на 24 години.
4. Повторний запит з тим самим ключем повертає збережений статус і тіло з заголовком `Idempotent-Replayed: true`, запису в базі не створюється.
5. Якщо перший запит ще виконується — `409 Conflict`. Якщо перший запит завершився помилкою — ключ видаляється, і клієнт може повторити.
6. Якщо Redis недоступний, запит із ключем отримує `503` (краще відмовити, ніж ризикувати дублікатом).

Redis спільний для всіх екземплярів, тому ключ працює незалежно від того, на який екземпляр потрапив повтор.
