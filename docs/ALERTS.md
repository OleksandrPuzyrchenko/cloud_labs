# Сповіщення

Файл: `app/terraform/alerts_scaling.tf`. Канал: SNS-топік `cloudlab-ops-notifications` з email-підпискою (`monitoring.tf`).

## Умова
Середнє CPU сервісу ECS **> 70% протягом 2 хвилин** (period 60 с, 2 з 2 точок). Alarm має `alarm_actions` (лист про проблему) і `ok_actions` (лист про повернення до норми).

### Обґрунтування
- CPU — прямий показник насичення, за ним працює і масштабування, тож сповіщення пов'язане з політикою (ціль 60%).
- 70% вище цілі масштабування: короткі піки та штатне додавання екземплярів не мають турбувати людину, але якщо навіть після масштабування CPU тримається вище 70% — це вже проблема.
- 2 хвилини відсікають одиничні сплески.

## Результат тесту
- Початок сталого навантаження: 12:50
- Перший лист (ALARM): 12:54
- Другий лист (OK): 12:59
- **Час від початку сталого навантаження до першого листа:** ~4 хв

## Чи прийнятний час реакції
Мінімальна затримка складається з періоду метрики (1 хв), двох точок оцінки (2 хв), затримки доставки CloudWatch → SNS → пошта (до хвилини). Тобто ~3–5 хв від початку проблеми. Для навчального сервісу це прийнятно; для реального — сумнівно для критичних систем: за 5 хв користувачі вже відчувають деградацію. Оскільки масштабування само реагує на навантаження, лист — це страховка, якщо автоматика не впоралася. Для критичних сервісів варто використовувати алерти за латентністю/помилками для користувача, коротший період (10–30 с) та доставку в месенджер/PagerDuty, а не лише пошту.
